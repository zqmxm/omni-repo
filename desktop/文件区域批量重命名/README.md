# 文件区域批量重命名

一个 Windows 桌面小工具：**从一堆 PDF / Word / Excel 文件的同一个固定位置读出文字，用这段文字给文件改名**。比如一批工程报告，每张表的「项目名称」都写在 B2 格，选一次 B2，整批文件就各自按自己 B2 里的内容命名。

## 这个软件干什么

- **PDF / Word**：预览是页面图，用鼠标在模板文件上拖一个框（比如框住「建设地点」那一行）。软件对每个文件只识别自己框内的图像，用内置中文 OCR 读出文字当文件名。框边切到半个字会自动补齐，表格线会被擦掉避免认出怪字。
- **Excel（.xls / .xlsx 都支持）**：预览是可选中格子的表格，点一下 `A1`、`B1`、`C2` 这样的格子，格子里是什么就命名什么。每个文件读自己同一个格子，不用装 Office。
- 批量导入、拖入文件夹、逐个预览核对、识别内容可双击改、一键改名、改完可撤销。
- 文件名自动清理非法字符、去空格、限长，重名加「（1）」「（2）」，扩展名固定保留。
- 识别不到内容的文件**自动跳过**，原名不动。

## 文件都是干什么的

| 文件 | 说明 |
| --- | --- |
| `app.py` | 主程序，全部功能都在这里（2724 行） |
| `build.bat` | 在本机重新打包成 exe 的脚本 |
| `launcher.c` | 单文件 exe 的启动器源码 |
| `_assemble.py` | 把 Windows 版 Python 运行时、依赖库、OCR 模型组装进单个 exe 的构建脚本 |
| `requirements.txt` | 依赖清单 |
| `VERSION` | 当前版本号 |
| `CHECKSUMS.md` | 成品 exe 的大小与校验值 |
| `历史说明/源码说明.md` | 两套模式的详细技术说明 |

## 怎么跑源码（Windows 10/11）

```
pip install -r requirements.txt
python app.py
```

## 怎么自己打出 exe

```
build.bat
```

产物在 `dist\FileAreaRenamer.exe`。

**注意**：`build.bat` 打出来的 exe **不含内置中文 OCR 模型**，需要自备 `rec.onnx` 放到 `ocr\` 目录。已经交付的成品 exe 是把模型一起塞进单文件的（所以有 127 MB），PDF 纯文字层抽取和 Excel 格子命名不依赖模型。

Word 要看原排版预览时，机器上装 LibreOffice（免费）或 Office / WPS 效果最好；都没有时程序会自动走内置文本重排，仍可读可框选，但版式与 WPS 不同，**请按软件里的预览重新拖一次框**。

## 怎么测试

打开软件导入 `_v32/` 那类样张（3 个 xlsx、2 个扫描 PDF、2 个 docx，样张是二进制，按仓库规矩没入库），分别验证：Excel 各取自身 B2、PDF 各自框选 OCR、`.doc` 免 Office、重名（1）、识别为空跳过、改名与撤销。

## 成品在哪下载

GitHub 本仓库 Releases 页 → **文件区域批量重命名-latest** → 显示名「文件区域批量重命名」的那个 exe。

历史交付时文件名叫 `FileAreaRenamer.exe`，内容完全一致，校验值见 `CHECKSUMS.md`。Release 里为了在网页上显示中文名，附件实际文件名是 ASCII 的 `FileAreaRenamer-windows-x64.exe`，**内容没变，CRC 一样**。

## 本软件不做什么

不联网、不上传任何文件、不读取账号信息。所有识别和改名都在本机完成。

## 边界（如实说）

- 成品 exe 做过静态校验和逻辑等价测试，**没有在 Windows 实机上跑过**。
- 成品体积 127 MB 是因为内置了中文 OCR 模型，超过 GitHub 仓库单文件 100 MB 上限，所以按仓库规矩**只放 Release，不进 git**。
- 这个成品含内置模型，CI 无法重建，因此**没有接入 `build-manifest.json` 自动构建**，也没有加 workflow。后续更新走 Release 覆盖。
